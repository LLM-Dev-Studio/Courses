# The Discover Phase

Discover establishes what is happening before the requested implementation
is treated as the answer. It has three fields.

## 1. Capture Request

Keep the original change request exactly as it arrived. You entered this
when you created the Initiative, so this field is already filled by the time
Discover starts.

## 2. Clarify Problem

Describe the problem, the affected people, and the pain points. Ask
questions such as:

> What problem would this request solve?

> Who is affected when the problem occurs?

> What happens today, and how often does it cause a problem?

## 3. Identify Impact

Make the current impact and evidence visible. Ask a question such as:

> What is the measurable cost of this problem today?

## Worked Example

A Facilitator, Priya, is running a session about the change request "Build a
mobile app so site supervisors can approve client variations faster." She
selects **Problem statement** and sends:

> What problem would a mobile variation approval app solve?

The Domain Expert, Daniel, answers:

> Variation requests often sit unresolved for several days. Site supervisors
> do not know who can approve them, and office staff frequently receive
> requests without enough information to price them. Work either stops while
> people wait, or continues before the cost is agreed.

Priya accepts this into the problem statement. Notice that the answer
describes the problem — not the mobile app that was originally requested.

> [!WARNING]
> Watch for answers that describe the requested solution instead of the
> underlying problem. If an answer only justifies the original request, ask a
> follow-up question that gets at what is actually going wrong.

## Key Takeaway

Discover exists to separate the problem from the request that named a
solution — keep asking until the problem statement stands on its own.
